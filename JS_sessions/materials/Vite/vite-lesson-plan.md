# План уроку: Основи Vite

**Тривалість:** 90 хвилин (можна скоротити до 60 — див. позначки ⏩)
**Рівень:** початковий / середній (студенти знають HTML, CSS, JavaScript, мають базове уявлення про npm)
**Актуальна версія:** Vite 8 (бандлер Rolldown, компілятор Oxc)

---

## 🎯 Цілі уроку

Після уроку студенти зможуть:

1. Пояснити, що таке бандлер і навіщо він потрібен.
2. Описати ключову різницю між підходом Webpack і Vite.
3. Створити проєкт на Vite та зрозуміти його структуру.
4. Пояснити, як працюють dev-сервер, нативні ES-модулі та HMR.
5. Налаштувати `vite.config.ts`: аліаси, плагіни, проксі, змінні середовища.
6. Зібрати production-версію та переглянути її через `vite preview`.

## 1. Вступ: навіщо потрібні бандлери (10 хв)

### Питання до аудиторії
> «Що станеться, якщо підключити 300 JS-файлів через `<script>` на сторінці?»

### Ключові тези
- **Проблеми без інструментів збірки:**
  - багато HTTP-запитів;
  - конфлікти глобальних змінних;
  - немає підтримки TypeScript, JSX, SCSS «з коробки»;
  - пакети з `node_modules` не працюють у браузері напряму (`import React from 'react'` — браузер не знає, де шукати);
  - немає мініфікації, tree-shaking, хешування файлів для кешу.
- **Бандлер** — інструмент, який бере граф модулів (від точки входу через усі `import`) і формує оптимізовані файли для браузера.
- **Основні задачі інструментів збірки:**
  - розв'язання імпортів (module resolution);
  - трансформація коду (TS → JS, JSX → JS, SCSS → CSS);
  - об'єднання та розбиття на чанки (bundling, code splitting);
  - оптимізація (мініфікація, tree-shaking);
  - dev-сервер з автоперезавантаженням.

## 2. Webpack vs Vite: два підходи (10 хв)

### Webpack (bundle-based dev server)
```
Старт dev-сервера:
[усі модулі] → [збірка всього бандла] → [сервер готовий]
```
- Перед запуском збирає **весь** застосунок.
- Що більший проєкт — то довший старт і повільніший HMR.
- Дуже гнучкий: loaders + plugins, але конфігурація часто складна.

### Vite (native ESM dev server)
```
Старт dev-сервера:
[сервер готовий одразу] → браузер запитує модуль → Vite трансформує лише його
```
- У режимі розробки **не бандлить** вихідний код — віддає його браузеру як нативні ES-модулі.
- Трансформує файли **на вимогу** (лише ті, які браузер реально запитав).
- Залежності з `node_modules` попередньо збираються один раз (**dependency pre-bundling**) і кешуються.
- Для production — повноцінна збірка бандлером.

### Еволюція «під капотом» (коротко)
| Версія | Dev / pre-bundling | Production build |
|--------|--------------------|------------------|
| Vite 2–7 | esbuild | Rollup |
| **Vite 8** | **Rolldown + Oxc** | **Rolldown** |

> 💡 Vite 8 замінив два різні інструменти одним бандлером **Rolldown**, написаним на Rust. Це прибрало розбіжності між dev і prod та суттєво пришвидшило збірку. API плагінів залишився сумісним із Rollup.

### Порівняльна таблиця
| Критерій | Webpack | Vite |
|----------|---------|------|
| Старт dev-сервера | Залежить від розміру проєкту | Майже миттєвий |
| HMR | Сповільнюється з ростом проєкту | Стабільно швидкий |
| Конфігурація | Об'ємна, багато loaders | Мінімальна, розумні дефолти |
| TS / JSX / CSS-модулі | Через loaders | З коробки |
| Екосистема | Дуже велика, зріла | Велика, швидко зростає |
| Типове використання | Легасі та складні enterprise-проєкти | Нові проєкти, React/Vue/Svelte, фреймворки (Nuxt, SvelteKit, Astro) |

## 3. Створення проєкту та структура (10 хв)

### Live-coding
```bash
npm create vite@latest my-vite-app
# обираємо: Vanilla → TypeScript (або React → TypeScript)
cd my-vite-app
npm install
npm run dev
```

### Структура проєкту
```
my-vite-app/
├── index.html          ← точка входу (!), лежить у корені
├── package.json
├── vite.config.ts      ← конфігурація (може бути відсутня)
├── tsconfig.json
├── public/             ← статичні файли, копіюються «як є»
│   └── favicon.svg
└── src/
    ├── main.ts         ← підключається з index.html
    ├── style.css
    └── assets/         ← ресурси, які обробляє Vite
```

### Акценти
- **`index.html` — точка входу**, а не JS-файл (на відміну від Webpack).
  ```html
  <script type="module" src="/src/main.ts"></script>
  ```
  Зверніть увагу на `type="module"` — це нативний ESM.
- Скрипти в `package.json`:
  ```json
  {
    "scripts": {
      "dev": "vite",
      "build": "tsc && vite build",
      "preview": "vite preview"
    }
  }
  ```
- **`public/` vs `src/assets/`:**
  - `public/` — файли не обробляються, доступні за абсолютним шляхом (`/favicon.svg`), імена не хешуються;
  - `src/assets/` — імпортуються в коді, оптимізуються, отримують хеш в імені.

## 4. Dev-сервер, ES-модулі та HMR (15 хв)

### Демо в DevTools → вкладка Network
1. Відкрити `http://localhost:5173`.
2. Показати, що браузер завантажує **окремі файли**: `main.ts`, `style.css`, `counter.ts`.
3. Відкрити `main.ts` у Network — показати, що TypeScript уже перетворено на JS.
4. Показати запит до `node_modules/.vite/deps/...` — це попередньо зібрані залежності.

### Dependency pre-bundling
**Навіщо:**
- пакети часто написані в CommonJS → їх треба перетворити на ESM;
- деякі пакети складаються з сотень дрібних модулів (наприклад, `lodash-es`) → без пре-бандлінгу браузер робив би сотні запитів.

Результат кешується в `node_modules/.vite`. Якщо щось «зламалось» — можна запустити `vite --force`.

### HMR (Hot Module Replacement)
**Демо:**
1. Збільшити лічильник на сторінці до, наприклад, 5.
2. Змінити колір у `style.css` → стиль оновився, **стан лічильника зберігся**.
3. Змінити текст у компоненті → оновився лише цей модуль.

**Як це працює (спрощено):**
```
Зміна файлу → Vite визначає модуль → WebSocket-повідомлення браузеру
→ браузер довантажує лише змінений модуль → заміна без перезавантаження сторінки
```

Для фреймворків (React, Vue) HMR налаштовують офіційні плагіни. Для vanilla JS — API `import.meta.hot`:
```ts
if (import.meta.hot) {
  import.meta.hot.accept((newModule) => {
    console.log('Модуль оновлено', newModule)
  })
}
```

## 5. Робота з ресурсами (10 хв)

### CSS
```ts
import './style.css'              // глобальні стилі
import styles from './card.module.css'  // CSS-модулі
element.className = styles.card
```
- **CSS-модулі** — файли `*.module.css`, класи ізолюються автоматично.
- **Препроцесори** — достатньо встановити пакет: `npm i -D sass` → імпортуємо `.scss`.
- PostCSS підхоплюється автоматично, якщо є `postcss.config.js`.

### Зображення та інші файли
```ts
import logoUrl from './assets/logo.png'        // URL (з хешем у build)
import iconRaw from './assets/icon.svg?raw'    // вміст як рядок
import workerUrl from './worker.js?url'        // явно отримати URL
```

### JSON
```ts
import { version } from '../package.json'  // іменований імпорт полів
```

### Динамічний імпорт (code splitting)
```ts
button.addEventListener('click', async () => {
  const { heavyFn } = await import('./heavy-module')
  heavyFn()
})
```
> У production `heavy-module` потрапить в окремий чанк і завантажиться лише після кліку.

## 6. Конфігурація `vite.config.ts` (15 хв)

### Базовий конфіг
```ts
import { defineConfig } from 'vite'
import react from '@vitejs/plugin-react'
import { fileURLToPath, URL } from 'node:url'

export default defineConfig({
  plugins: [react()],

  resolve: {
    alias: {
      '@': fileURLToPath(new URL('./src', import.meta.url)),
    },
  },

  server: {
    port: 3000,
    open: true,
    proxy: {
      '/api': {
        target: 'http://localhost:8080',
        changeOrigin: true,
      },
    },
  },

  build: {
    outDir: 'dist',
    sourcemap: true,
  },
})
```

### Розбір по пунктах
| Опція | Що робить | Приклад використання |
|-------|-----------|----------------------|
| `plugins` | Підключає плагіни | React, Vue, PWA, SVG-компоненти |
| `resolve.alias` | Короткі шляхи | `import Button from '@/components/Button'` |
| `server.proxy` | Проксіювання запитів | Обхід CORS під час розробки з бекендом |
| `build.outDir` | Папка збірки | `dist` за замовчуванням |
| `build.rolldownOptions` | Тонке налаштування бандлера (Vite 8) | Власні правила розбиття на чанки |

> ⚠️ У Vite 7 і старіших замість `build.rolldownOptions` використовувалась опція `build.rollupOptions` — її досі можна зустріти в туторіалах.

> 💡 Для аліасів у TypeScript потрібно також додати `paths` у `tsconfig.json`, інакше редактор показуватиме помилки.

### Змінні середовища
Файли: `.env`, `.env.local`, `.env.development`, `.env.production`

```bash
# .env
VITE_API_URL=https://api.example.com
DB_PASSWORD=secret   # ❌ НЕ потрапить у клієнтський код
```
```ts
console.log(import.meta.env.VITE_API_URL)  // ✅ доступно
console.log(import.meta.env.MODE)           // 'development' | 'production'
console.log(import.meta.env.DEV)            // true / false
```
**Важливо:** у клієнтський код потрапляють лише змінні з префіксом `VITE_`. Це захист від випадкового витоку секретів.

### Плагіни
- Vite використовує API плагінів, сумісний із Rollup → велика екосистема.
- Каталог плагінів: <https://registry.vite.dev>
- Мінімальний власний плагін (для розуміння концепції):
```ts
function myPlugin() {
  return {
    name: 'my-plugin',
    transform(code: string, id: string) {
      if (id.endsWith('.ts')) {
        return code.replace('__BUILD_TIME__', JSON.stringify(new Date().toISOString()))
      }
    },
  }
}
```

## 7. Production build і preview (10 хв)

### Демо
```bash
npm run build
npm run preview   # локальний сервер для перевірки збірки (порт 4173)
```

### Що показати в папці `dist/`
```
dist/
├── index.html
├── favicon.svg                ← з public/, без змін
└── assets/
    ├── index-a1b2c3d4.js      ← хеш у назві
    ├── heavy-module-e5f6.js   ← окремий чанк (динамічний імпорт)
    └── index-9f8e7d6c.css
```

### Що відбувається під час build
- **Tree-shaking** — видалення невикористаного коду.
- **Мініфікація** JS і CSS.
- **Code splitting** — розбиття на чанки.
- **Хешування імен** — для довготривалого кешування в браузері.
- **Оптимізація ресурсів** — дрібні файли можуть вбудовуватись як base64.

### Важливо пояснити
- `vite preview` — **не** production-сервер, а інструмент для локальної перевірки.
- `dist/` — це статичні файли, їх можна розмістити на будь-якому хостингу (Netlify, Vercel, GitHub Pages, Nginx).
- Якщо сайт розміщується не в корені домену — опція `base: '/my-repo/'` у конфігу (типово для GitHub Pages).

⏩ *Для 60-хвилинної версії: скоротити блоки 2 і 5 до 5 хв, пропустити власний плагін у блоці 6 та практику, дати її як домашнє завдання.*

## 8. Практика та підсумки (10 хв)

### Практичне завдання (5–7 хв)
У створеному проєкті:
1. Додати аліас `@` → `src`.
2. Створити файл `.env` зі змінною `VITE_APP_TITLE` і вивести її на сторінці.
3. Створити модуль `src/utils/heavy.ts` і підключити його через динамічний імпорт по кліку кнопки.
4. Виконати `npm run build` і знайти окремий чанк у `dist/assets`.

### Швидкий квіз (усно)
1. Чому dev-сервер Vite стартує швидше, ніж у Webpack?
   → *Не збирає весь застосунок, віддає модулі як нативний ESM і трансформує їх на вимогу.*
2. Що є точкою входу у Vite-проєкті?
   → *`index.html`.*
3. Яка різниця між `public/` і `src/assets/`?
   → *`public/` копіюється без обробки; `assets/` обробляються та хешуються.*
4. Чому змінна `API_SECRET` з `.env` недоступна в коді?
   → *Немає префікса `VITE_`.*
5. Який бандлер використовує Vite 8 для production-збірки?
   → *Rolldown.*
6. Навіщо потрібен dependency pre-bundling?
   → *Перетворити CommonJS на ESM і зменшити кількість запитів від пакетів з багатьма модулями.*

### Підсумок (2 хв)
- Бандлери вирішують проблеми модулів, трансформації та оптимізації.
- Vite розділяє dev (нативний ESM, швидкий HMR) і production (повна оптимізована збірка).
- Мінімальна конфігурація + розумні дефолти + сумісна екосистема плагінів.
