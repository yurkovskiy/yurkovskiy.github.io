# Віртуалізація, контейнеризація та Docker: Теоретичні основи й практика

Цей посібник охоплює ключові концепції сучасного розгортання додатків: від фундаментальних механізмів ядра Linux до керування багатоконтейнерними середовищами за допомогою Docker Compose.

## 1. Віртуалізація vs Контейнеризація

Обидві технології дозволяють ізолювати додатки та ефективно використовувати ресурси сервера, але працюють на різних рівнях абстракції.

### Віртуальні машини (Virtual Machines — VM)

* **Архітектура:** Використовують **гіпервізор** (KVM, VMware, Hyper-V), який емулює апаратне забезпечення.

* **Ізоляція:** Повна. Кожна ВМ має власну повноцінну гостьову операційну систему (ОС) та власне ядро.

* **Недоліки:** Великий розмір образів (гігабайти), повільний запуск (хвилини), високі накладні витрати оперативної пам'яті та процесора на роботу гостьових ОС.

### Контейнери (Containers)

* **Архітектура:** Використовують спільне ядро хостової ОС. Ізоляція забезпечується на рівні процесів.

* **Ізоляція:** На рівні простору користувача (user space).

* **Переваги:** Миттєвий запуск (мілісекунди/секунди), малий розмір (мегабайти), мінімальні накладні витрати ресурсів.

| Критерій | Віртуальні машини (VM) | Контейнери (Docker) | 
| ----- | ----- | ----- | 
| **Рівень ізоляції** | Апаратний (через гіпервізор) | Рівень ОС (ядро Linux) | 
| **Ядро ОС** | У кожної ВМ своє ядро | Спільне ядро хоста | 
| **Час запуску** | Хвилини | Секунди / мілісекунди | 
| **Споживання ресурсів** | Високе (ГБ RAM на ОС) | Низьке (тільки ресурси процесу) | 
| **Безпека** | Вища (повна ізоляція) | Залежить від налаштувань ядра | 

## 2. Фундамент контейнерів у Linux: Namespaces та cgroups

Контейнери — це не магія, а комбінація вбудованих механізмів ядра Linux.

### Linux Namespaces (Простори імен)

**Namespaces** визначають, *що процес може бачити*. Вони ізолюють глобальні системні ресурси так, щоб процеси всередині контейнера вважали, що вони працюють в окремій ОС.

Основні типи просторів імен:

1. **PID (Process ID):** Ізолює дерево процесів. Процес усередині контейнера може мати `PID 1`, хоча на хості він має, наприклад, `PID 14820`.

2. **NET (Network):** Надає власний мережевий стек: мережеві інтерфейси, IP-адреси, таблиці маршрутизації та порти.

3. **MNT (Mount):** Ізолює точки монтування файлової системи. Контейнер бачить власну кореневу директорію (`/`).

4. **UTS (UNIX Time-Sharing):** Дозволяє контейнеру мати власне ім'я хоста (`hostname`) та доменне ім'я.

5. **IPC (Inter-Process Communication):** Ізолює ресурси міжпроцесної взаємодії (спільну пам'ять, черги повідомлень).

6. **USER:** Дозволяє зіставляти ідентифікатори користувачів (UID/GID) всередині контейнера з іншими ідентифікаторами на хості (наприклад, `root` у контейнері може бути звичайним користувачем на хості).

### Control Groups (cgroups)

**cgroups** визначають, *скільки ресурсів процес може споживати*. Вони обмежують, обліковують та ізолюють використання апаратних ресурсів для груп процесів:

* **CPU:** Обмеження процесорного часу або прив'язка до конкретних ядер.

* **Memory:** Ліміт оперативної пам'яті (при перевищенні спрацьовує OOM Killer).

* **Block I/O:** Обмеження швидкості читання/запису на диск.

* **Network:** Пріоритезація та обмеження мережевого трафіку.

## 3. Що таке Docker та його архітектура

**Docker** — це платформа для розробки, доставки та запуску додатків у контейнерах.

### Ключові компоненти:

* **Docker Daemon (`dockerd`):** Фоновий процес на хості, який керує образами, контейнерами, мережами та томами.

* **Docker Client (`docker`):** Інструмент командного рядка (CLI), через який користувач взаємодіє з демоном за допомогою REST API.

* **Docker Image (Образ):** Незмінний (read-only) шаблон, що складається з шарів (layers), який містить код додатку, бібліотеки, залежності та конфігурацію.

* **Docker Container (Контейнер):** Запущений екземпляр образу. Додає поверх шарів образу один тонкий шар для запису (read-write layer).

* **Docker Registry:** Репозиторій для зберігання та розповсюдження образів (наприклад, Docker Hub, GitHub Container Registry).

## 4. Основні команди Docker CLI

### Робота з образами (Images)

```bash
# Завантажити образ із Docker Hub
docker pull nginx:latest

# Показати список локальних образів
docker images

# Зібрати власний образ із Dockerfile у поточній директорії
docker build -t my-app:1.0 .

# Видалити образ
docker rmi nginx:latest
```

### Життєвий цикл контейнерів (Containers)

```bash
# Запустити контейнер у фоновому режимі (-d) з прокиданням портів (-p хост:контейнер) та ім'ям (--name)
docker run -d --name my-nginx -p 8080:80 nginx:latest

# Показати запущені контейнери
docker ps

# Показати всі контейнери (включно із зупиненими)
docker ps -a

# Зупинити та запустити контейнер
docker stop my-nginx
docker start my-nginx

# Видалити зупинений контейнер (або примусово з -f)
docker rm -f my-nginx
```

### Налагодження та моніторинг

```bash
# Переглянути логи контейнера в реальному часі (-f)
docker logs -f my-nginx

# Виконати інтерактивну оболонку (bash або sh) всередині запущеного контейнера
docker exec -it my-nginx /bin/bash

# Переглянути використання ресурсів (CPU, RAM, мережа) у реальному часі
docker stats

# Отримати детальну інформацію про контейнер у форматі JSON
docker inspect my-nginx
```

### Робота з даними (Volumes) та мережами (Networks)

```bash
# Створити іменований том (volume) для збереження даних після видалення контейнера
docker volume create pg_data

# Запустити PostgreSQL із підключеним томом
docker run -d --name postgres-db -e POSTGRES_PASSWORD=secret -v pg_data:/var/lib/postgresql/data postgres:16

# Створити ізольовану мережу типу bridge
docker network create app-network

# Очистити систему від невикористовуваних контейнерів, мереж та кешу
docker system prune
```

## 5. Приклад Dockerfile

`Dockerfile` — це текстовий файл з інструкціями для автоматичної збірки образу.

```dockerfile
# Використовуємо легкий базовий образ Python
FROM python:3.11-slim

# Встановлюємо робочу директорію всередині контейнера
WORKDIR /app

# Копіюємо файл залежностей та встановлюємо їх (кешування шарів)
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

# Копіюємо решту коду додатку
COPY . .

# Вказуємо порт, який слухає додаток (документаційна інструкція)
EXPOSE 8000

# Команда для запуску додатку при старті контейнера
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]
```

## 6. Docker Compose

**Docker Compose** — це інструмент для визначення та запуску багатоконтейнерних додатків. Уся конфігурація описується в одному YAML-файлі (`docker-compose.yml`).

### Приклад `docker-compose.yml` (Веб-додаток + База даних PostgreSQL + Redis)

```yaml
services:
  # Сервіс веб-додатку
  web:
    build: .
    container_name: fastapi_app
    ports:
      - "8000:8000"
    environment:
      - DATABASE_URL=postgresql://user:password@db:5432/mydatabase
      - REDIS_URL=redis://cache:6379/0
    depends_on:
      db:
        condition: service_healthy
      cache:
        condition: service_started
    networks:
      - backend_net
    restart: unless-stopped

  # Сервіс бази даних
  db:
    image: postgres:16-alpine
    container_name: postgres_db
    environment:
      POSTGRES_USER: user
      POSTGRES_PASSWORD: password
      POSTGRES_DB: mydatabase
    volumes:
      - postgres_data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U user -d mydatabase"]
      interval: 5s
      timeout: 5s
      retries: 5
    networks:
      - backend_net

  # Сервіс кешування
  cache:
    image: redis:7-alpine
    container_name: redis_cache
    networks:
      - backend_net

# Іменовані томи для постійного зберігання даних
volumes:
  postgres_data:

# Ізольована мережа для взаємодії сервісів за їх іменами (db, cache)
networks:
  backend_net:
    driver: bridge
```

### Основні команди Docker Compose

```bash
# Зібрати образи та запустити всі сервіси у фоновому режимі
docker compose up -d --build

# Переглянути статус сервісів проєкту
docker compose ps

# Переглянути логи конкретного сервісу (наприклад, web)
docker compose logs -f web

# Зупинити та видалити контейнери і мережі (томи залишаються)
docker compose down

# Зупинити та видалити все, включно з томами (-v)
docker compose down -v
```

## 7. Обмеження апаратних ресурсів контейнера (CPU, RAM, Disk I/O)

За замовчуванням контейнер не має обмежень і може спожити всі доступні ресурси хостової машини. Для контролю використовуються механізми **Linux cgroups**, які налаштовуються через прапорці Docker CLI або секцію `deploy.resources` у Docker Compose.

### Налаштування через Docker CLI

```bash
docker run -d \
  --name worker-app \
  # --- Обмеження процесора (CPU) ---
  --cpus="1.5" \                # Максимум 1.5 ядра CPU (150% процесорного часу)
  --cpuset-cpus="0,2" \         # Прив'язка виключно до 0-го та 2-го фізичних/логічних ядер
  --cpu-shares=512 \            # Відносний пріоритет CPU при високому навантаженні (за замовчуванням 1024)
  # --- Обмеження пам'яті (RAM та Swap) ---
  --memory="512m" \             # Жорсткий ліміт оперативної пам'яті (512 МБ)
  --memory-reservation="256m" \ # М'який ліміт (гарантований мінімум при дефіциті RAM на хості)
  --memory-swap="1g" \          # Загальний ліміт RAM + Swap (тобто 512 МБ RAM + 512 МБ Swap). Якщо вказати "512m" (рівно --memory), swap буде вимкнено
  --oom-kill-disable=false \    # Дозволити ядру вбити процес (OOM Killer) при перевищенні ліміту RAM
  # --- Обмеження диску (Block I/O) та кількості процесів ---
  --device-read-bps="/dev/sda:10mb" \   # Максимальна швидкість читання з диска (10 МБ/с)
  --device-write-bps="/dev/sda:5mb" \   # Максимальна швидкість запису на диск (5 МБ/с)
  --pids-limit=100 \                    # Максимальна кількість процесів/потоків усередині контейнера (захист від fork-бомб)
  my-app:1.0
```

#### Зміна лімітів на льоту (без перезапуску контейнера)

За допомогою команди `docker update` можна змінити виділені ресурси для вже запущеного контейнера:

```bash
# Збільшити ліміт пам'яті до 1 ГБ та виділити 2 ядра CPU
docker update --memory="1g" --memory-swap="1g" --cpus="2.0" worker-app
```

### Налаштування через Docker Compose

У файлі `docker-compose.yml` ліміти (limits) та гарантовані резерви (reservations) задаються в блоці `deploy.resources`:

```yaml
services:
  heavy_worker:
    image: my-app:1.0
    container_name: heavy_worker
    cpuset: "0,1"               # Прив'язка до конкретних ядер (0 та 1)
    pids_limit: 200             # Ліміт процесів усередині контейнера
    memswap_limit: 1g           # Ліміт RAM + Swap
    deploy:
      resources:
        # Максимально дозволені ресурси (жорсткий ліміт)
        limits:
          cpus: '2.0'           # Не більше 2 ядер CPU
          memory: 1G            # Не більше 1 ГБ RAM
        # Гарантовані ресурси, які Docker зарезервує для контейнера
        reservations:
          cpus: '0.5'           # Мінімум 0.5 ядра CPU
          memory: 256M          # Мінімум 256 МБ RAM
```

> **Примітка:** Якщо програма всередині контейнера перевищить жорсткий ліміт `memory` (і вичерпає доступний `swap`), ядро Linux завершить її з помилкою **OOMKilled (Exit Code 137)**. Перевірити, чи був контейнер зупинений через нестачу пам'яті, можна командою:
> `docker inspect worker-app --format='{{.State.OOMKilled}}'`
