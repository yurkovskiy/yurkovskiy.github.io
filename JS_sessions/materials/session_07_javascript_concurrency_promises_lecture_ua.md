# Модуль 1: Архітектура конкурентності в JavaScript

### 1.1 Однопотоковість, принцип Run-to-Completion та Стек викликів (Call Stack)

JavaScript проєктувався як **однопотокове, неблокуюче, подієво-орієнтоване** середовище виконання. «Однопотоковість» означає, що один агент JavaScript (інстанс рушія V8 або JavaScriptCore) володіє рівно **одним стеком викликів (Call Stack)** і в кожен окремий момент часу виконує лише одну інструкцію.

```
       +---------------------------------------------+
       |           СТЕК ВИКЛИКІВ (CALL STACK)        |
       |  +---------------------------------------+  |
       |  | computeHash()                         |  |  <-- Фрейм стека (Pushed)
       |  +---------------------------------------+  |
       |  | validateCredentials()                 |  |
       |  +---------------------------------------+  |
       |  | handleLogin()                         |  |
       |  +---------------------------------------+  |
       |  | (anonymous / global execution context)|  |
       |  +---------------------------------------+  |
       +---------------------------------------------+
                              |
                     Run-to-Completion
                              v
```

#### Інваріант Run-to-Completion (Виконання до кінця)

Щойно фрейм стека або ланцюжок вкладених викликів починає виконання, він не може бути перерваний чи витіснений іншим фрагментом коду JavaScript. Функція, яка наразі знаходиться у стеку викликів, виконується безперервно доки не поверне значення або не згенерує виняток, тим самим повністю звільнивши активні фрейми.

У чистому виконанні ECMAScript відсутні апаратні переривання потоків, м'ютекси або умовні змінні. Конкурентність досягається не одночасним виконанням декількох сценаріїв, а завдяки **Event Loop (циклу подій)**, який делегує та запускає ізольовані блоки коду, коли стек викликів стає абсолютно порожнім.

### 1.2 Купа пам'яті (Memory Heap) та Фрейми стека

* **Стек викликів (Call Stack):** Відстежує контексти виконання. Щоразу, коли викликається функція, виділяється новий фрейм стека, що містить:
  1. Примітивні локальні змінні.
  2. Адреси повернення для відновлення виконання.
  3. Ідентифікатори контексту (`this`, посилання на лексичні області видимості).
* **Купа пам'яті (Memory Heap):** Неструктурований простір оперативної пам'яті, де зберігаються посилальні типи (об'єкти, масиви, функції, замикання). Покажчики зі стека вказують на адреси всередині купи. Збирач сміття (Garbage Collector, наприклад, Generational Scavenge та Mark-Sweep-Compact у V8) періодично сканує цей простір для звільнення неактивних об'єктів.

### 1.3 Хост-середовище: Web APIs та Libuv

Чиста специфікація ECMAScript визначає типи даних, синтаксис та контексти виконання, але **не містить опису таймерів, мережевих запитів, файлового введення/виведення чи планувальників потоків**. Ці можливості надаються **хост-середовищем**:

```
+---------------------------------------------------------------------------+
|                      ХОСТ-СЕРЕДОВИЩЕ (Браузер / Node.js)                  |
|                                                                           |
|   +-----------------------+      +------------------------------------+   |
|   |       JS РУШІЙ        |      |             ХОСТ-APIs              |   |
|   |      (напр. V8)       |      |                                    |   |
|   |                       |      |  - DOM Events / MutationObserver   |   |
|   |  +-----------------+  |      |  - fetch / XMLHttpRequest          |   |
|   |  |   Call Stack    |  |      |  - setTimeout / setInterval        |   |
|   |  +-----------------+  |      |  - fs / net / crypto (Node.js)     |   |
|   |  |   Memory Heap   |  |      |                                    |   |
|   |  +-----------------+  |      +------------------------------------+   |
|   +-----------------------+                         |                     |
|              ^                                      | (Передає колбек     |
|              |                                      |  після завершення   |
|              |                                      |  операції I/O)      |
|              |                                      v                     |
|   +-------------------------------------------------------------------+   |
|   |                           EVENT LOOP                              |   |
|   |                                                                   |   |
|   |   [Черга мікротасків] <----- Promises, queueMicrotask             |   |
|   |   [Черга макротасків] <----- Таймери, мережа, події інтерфейсу    |   |
|   +-------------------------------------------------------------------+   |
+---------------------------------------------------------------------------+
```

Коли викликається `setTimeout(callback, 1000)`:
1. Рушій JS реєструє таймер у фоновій інфраструктурі хоста (C++ пул таймерів або системний таймер ядра).
2. Стек викликів JS негайно звільняється, не чекаючи завершення секунди.
3. Через 1000 мс хост-середовище поміщає переданий колбек у **чергу завдань (Task Queue)**.
4. Event Loop чекає моменту, коли стек викликів спорожніє, після чого забирає колбек і поміщає його в стек викликів на виконання.

# Модуль 2: Event Loop та Черги завдань

### 2.1 Анатомія одного оберту (Tick) циклу подій

Event Loop — це неперервний цикл усередині хост-середовища. Його алгоритмічний потік чітко зафіксований стандартом HTML Living Standard (для браузерів) та фазовою моделлю Libuv (для Node.js).

Один цикл оберту браузерного Event Loop виглядає так:

1. **Вибір найстарішого макротаска:** Перевірити черги макротасків. Якщо завдання готове, взяти його та виконувати в Call Stack до повного завершення.
2. **Очищення черги мікротасків (Microtask Checkpoint):** Запустити виконання *кожного* завдання з черги мікротасків у порядку FIFO. Якщо виконання мікротаска додає *ще один* мікротаск, він також негайно додається до черги і виконується в цьому ж циклі. Робота триває доти, доки черга мікротасків не стане абсолютно порожньою ($0$ елементів).
3. **Можливість рендерингу (тільки в браузерах):**
   * Перевірити, чи екран потребує оновлення кадру (зазвичай синхронізовано з частотою оновлення монітора: $60\text{Hz} = 16.6\text{ms}$, $120\text{Hz} = 8.3\text{ms}$).
   * Виконати колбеки `requestAnimationFrame` (rAF).
   * Запустити перерахунок стилів CSS, обчислення геометрії (reflow/layout) та промальовування (paint/composite).
4. **Очікування (Idle/Sleep):** Якщо черги завдань і мікротасків порожні, потік переходить у режим сну до надходження нової події (наприклад, мережевого пакета, кліку миші або спрацьовування таймера).

### 2.2 Черга макротасків проти Черги мікротасків

| Характеристика | Черга макротасків (Task Queue) | Черга мікротасків (Microtask Queue) |
| :--- | :--- | :--- |
| **Типові джерела** | `setTimeout`, `setInterval`, `setImmediate` (Node.js), DOM-події, взаємодія користувача, мережеве I/O. | `Promise.then/catch/finally`, `queueMicrotask`, `MutationObserver`. |
| **Обсяг вибірки за один такт** | Рівно **один** макротаск за цикл перед повторною перевіркою мікротасків та рендерингу. | **Усі** доступні мікротаски, доки черга повністю не вичерпається. |
| **Пріоритет витіснення** | Не може переривати код або обганяти мікротаски. | Має абсолютний пріоритет, щойно Call Stack звільняється. |
| **Зв'язок із рендерингом** | Браузер може виконати перемальовування екрана між макротасками. | Браузер **не може** оновити екран, доки всі мікротаски не виконаються. |

### 2.3 Детальна архітектурна діаграма

```
                     +---------------------------+
                     |  Стек викликів стає       |
                     |         ПОРОЖНІМ          |
                     +---------------------------+
                                   |
                                   v
                    /-----------------------------\
                   |   Чи є завдання в             |
                   |   Черзі мікротасків?          |
                    \-----------------------------/
                             /              \
                     ТАК    /                \  НІ
                           v                  v
       +-------------------------+     /-----------------------------\
       | Витягти та виконати     |    |   Чи час рендерити           |
       | ОДИН мікротаск          |    |   новий кадр на екрані?      |
       +-------------------------+     \-----------------------------/
                   |                               /              \
                   |                       ТАК    /                \  НІ
                   +-------+                     v                  v
                           |          +--------------------+  +----------------------+
                           |          | 1. Resize/Scroll   |  | Взяти НАСТУПНИЙ      |
                           |          | 2. rAF колбеки     |  | макротаск із         |
                           |          | 3. Layout (Reflow) |  | Черги завдань        |
                           |          | 4. Paint           |  +----------------------+
                           |          +--------------------+             |
                           |                     |                       v
                           |                     +--------> +------------------------+
                           |                                | Передати макротаск у   |
                           |                                | Call Stack та виконати |
                           |                                +------------------------+
                           |                                             |
                           +---------------------------------------------+
```

### 2.4 Взаємодія з конвеєром рендерингу браузера

Фундаментальна практична відмінність між макро- та мікротасками полягає в їхньому впливі на інтерфейс:

* **Макротаски дають браузеру змогу рендерити.** Оскільки браузер перевіряє необхідність оновлення графіки після очищення мікротасків та після завершення кожного окремого макротаска, планування важких операцій через ланцюжок `setTimeout(..., 0)` дає рушію можливість своєчасно малювати кадри, зберігаючи плавність анімацій.
* **Мікротаски блокують рендеринг.** Браузер не змінить жодного пікселя на моніторі, доки не спустошить чергу мікротасків. Якщо ланцюжок мікротасків обчислюється $500\text{мс}$, користувач бачитиме застиглу сторінку, а інтерфейс взагалі не реагуватиме на натискання.

# Модуль 3: Поглиблений аналіз мікротасків

### 3.1 Джерела мікротасків

У сучасному стандарті JavaScript існує три основні канали генерації мікротасків:

1. **Проміси:** Колбеки, передані в `.then()`, `.catch()` та `.finally()`.
2. **Явний виклик:** Стандартний глобальний метод `queueMicrotask(fn)`.
3. **DOM MutationObserver:** Колбеки спостереження за змінами в дереві DOM.

```javascript
// 1. Явне планування через queueMicrotask
queueMicrotask(() => {
  console.log("Виконано явний мікротаск");
});

// 2. Реакція проміса
Promise.resolve("Дані").then(result => {
  console.log("Реакція проміса як мікротаск:", result);
});

// 3. MutationObserver (у браузері)
if (typeof MutationObserver !== "undefined") {
  const observer = new MutationObserver((mutations) => {
    console.log("Мікротаск мутації DOM виконано");
  });
  observer.observe(document.body, { attributes: true });
}
```

### 3.2 Інваріант вичерпання черги мікротасків (Microtask Drainage)

Специфікація ECMAScript вимагає: щойно глибина активного стека викликів падає до нуля, рушій негайно ініціює точку перевірки мікротасків (**Microtask Checkpoint**):

$$
\text{DrainMicrotasks}() \implies \text{while } (\text{Queue}_{\text{micro}} \neq \emptyset) \ \{ \text{task} = \text{dequeue}();\ \text{run}(\text{task}); \}
$$

Якщо поточний мікротаск ставить у чергу новий мікротаск, умова циклу залишається істинною ($\text{Queue}_{\text{micro}} \neq \emptyset$). Процес триватиме безперервно, доки черга не спорожніє повністю.

### 3.3 Голодування Event Loop та зависання інтерфейсу (Пастка мікротасків)

Нижче наведено класичний приклад блокування основного потоку нескінченними мікротасками:

```javascript
// Макротаск, який намагається виконатися якнайшвидше
setTimeout(() => {
  console.log("Макротаск: цей рядок НІКОЛИ не виведеться, якщо виникло голодування!");
}, 0);

let iteration = 0;

function starveLoopForever() {
  iteration++;
  // Рекурсивно додаємо мікротаск
  queueMicrotask(() => {
    if (iteration < 1_000_000) {
      starveLoopForever();
    } else {
      console.log("Мікротасковий шторм нарешті зупинено.");
    }
  });
}

starveLoopForever();
console.log("Синхронне виконання основного скрипту завершено.");
```

#### Чому це блокує все?
Колбек `setTimeout` знаходиться в черзі макротасків. Event Loop принципово не переходить до вибірки макротасків, доки в черзі мікротасків залишається бодай один елемент. Оскільки кожен мікротаск породжує наступний, стек очищується лише на частку секунди і знову заповнюється мікротаском, спричиняючи повне **голодування (starvation)** таймерів, мережевих обробників та рендерингу сторінки.

### 3.4 Специфіка Node.js: `process.nextTick()` проти стандартних мікротасків

У середовищі Node.js реалізована власна черга мікрозавдань, яка має вищий пріоритет, ніж стандартна черга промісів: **`nextTickQueue`**.

```
Стек викликів звільняється
       |
       v
[ Черга process.nextTick ]  <--- Найвищий пріоритет (виконується до повного очищення)
       |
       v
[ Черга мікротасків (Promises, queueMicrotask) ] <--- Виконується другою
       |
       v
[ Фази Libuv (Timers -> I/O Callbacks -> Poll -> Check/setImmediate -> Close) ]
```

```javascript
// Приклад для середовища Node.js
setTimeout(() => console.log("1. Макротаск (Timer)"), 0);

Promise.resolve().then(() => console.log("3. Стандартний мікротаск (Promise)"));

queueMicrotask(() => console.log("4. Стандартний мікротаск (queueMicrotask)"));

process.nextTick(() => console.log("2. Колбек process.nextTick"));

console.log("0. Синхронний старт");

// Послідовність виводу:
// 0. Синхронний старт
// 2. Колбек process.nextTick
// 3. Стандартний мікротаск (Promise)
// 4. Стандартний мікротаск (queueMicrotask)
// 1. Макротаск (Timer)
```

Колбеки, зареєстровані через `process.nextTick()`, потрапляють у внутрішню системну чергу і відпрацьовують одразу після поточної операції ще до того, як рушій почне обробляти стандартні мікротаски Promises/`queueMicrotask`.

# Модуль 4: Проміси — Архітектура та внутрішні стани

### 4.1 Анатомія Promise: Стани, реакції та обробники

Згідно зі специфікацією ECMAScript, `Promise` — це системний об'єкт, який є обгорткою над значенням, що може стати доступним зараз, у майбутньому або ніколи. Внутрішня структура проміса включає такі приховані поля (Internal Slots):

1. `[[PromiseState]]`: `"pending"` (очікування), `"fulfilled"` (виконано) або `"rejected"` (відхилено).
2. `[[PromiseResult]]`: `undefined` (доки стан pending), фінальне значення успіху або причина помилки.
3. `[[PromiseFulfillReactions]]` та `[[PromiseRejectReactions]]`: Списки записів (reaction records), які містять функції зворотного виклику, додані через `.then()`, `.catch()` або `.finally()`.

```
                  +-----------------------------------+
                  |          ОБ'ЄКТ PROMISE           |
                  |                                   |
                  |  [[PromiseState]]:  "pending"     |
                  |  [[PromiseResult]]: undefined     |
                  |  [[PromiseFulfillReactions]]: []  |
                  |  [[PromiseRejectReactions]]:  []  |
                  +-----------------------------------+
                                    |
                    +---------------+---------------+
                    |                               |
       resolve(value)                               reject(reason)
                    v                               v
    +-------------------------------+   +-------------------------------+
    | [[PromiseState]]: "fulfilled" |   | [[PromiseState]]: "rejected"  |
    | [[PromiseResult]]: value      |   | [[PromiseResult]]: reason     |
    +-------------------------------+   +-------------------------------+
                    |                               |
                    v                               v
    Формує мікротаски для              Формує мікротаски для
    [[PromiseFulfillReactions]]         [[PromiseRejectReactions]]
```

#### Правила переходу станів:

1. Проміс може перейти зі стану `"pending"` у стан `"fulfilled"` лише **один раз**.
2. Проміс може перейти зі стану `"pending"` у стан `"rejected"` лише **один раз**.
3. Зміна стану є **незворотною**. Щойно проміс перейшов у стан settled (fulfilled або rejected), його результат остаточно зафіксовано. Усі наступні виклики `resolve()` або `reject()` ігноруються.

```javascript
const p = new Promise((resolve, reject) => {
  resolve("Перше рішення");
  reject(new Error("Друге рішення")); // Повністю ігнорується!
  resolve("Третє рішення");           // Повністю ігнорується!
});

p.then(val => console.log("Результат:", val)); // Виведе: Результат: Перше рішення
```

### 4.2 Постановка реакцій у чергу: чому `.then()` завжди асинхронний

Поширена помилка новачків: думати, що якщо Promise вже заздалегідь вирішений (fulfilled), його обробник `.then()` виконається синхронно. **Це неможливо за специфікацією.** Колбек реакції проміса завжди ставиться в чергу мікротасків.

```javascript
const resolvedPromise = Promise.resolve("Мить");

console.log("До додавання .then()");

resolvedPromise.then((val) => {
  console.log("Всередині обробника:", val);
});

console.log("Після додавання .then()");

// Порядок виводу:
// До додавання .then()
// Після додавання .then()
// Всередині обробника: Мить
```

#### Навіщо це зроблено?
Такий підхід повністю нівелює помилку **«Zälgo»** (коли функція за одних обставин поводиться синхронно, а за інших асинхронно, порушуючи передбачуваність стану програми). Проміси забезпечують 100% передбачувану черговість подій.

### 4.3 Механіка ланцюжків промісів та розгортання thenable-об'єктів

Кожен виклик `.then()` повертає **новий незалежний об'єкт Promise**. Стан і значення цього повернутого проміса визначаються тим, що саме повернув колбек у `.then()`:

```
Крок 1: Батьківський Promise переходить у fulfilled зі значенням V1.
Крок 2: Викликається onFulfilled(V1).
Крок 3:
   Сценарій A: Повертає звичайне значення R2 --> Дочірній Promise переходить у fulfilled(R2).
   Сценарій B: Викидає помилку throw E      --> Дочірній Promise переходить у rejected(E).
   Сценарій C: Повертає інший Promise P2    --> Дочірній Promise зв'язується зі станом і значенням P2.
```

```javascript
Promise.resolve(10)
  .then((num) => {
    console.log("Крок 1:", num); // 10
    return num * 2;              // Сценарій A: повертаємо просте значення
  })
  .then((doubled) => {
    console.log("Крок 2:", doubled); // 20
    // Сценарій C: повертаємо новий Promise (Thenable unwrapping)
    return new Promise((resolve) => {
      setTimeout(() => resolve(doubled + 5), 100);
    });
  })
  .then((finalValue) => {
    console.log("Крок 3 (із затримкою):", finalValue); // 25
    throw new Error("Аварія в конвеєрі!");             // Сценарій B
  })
  .catch((err) => {
    console.error("Помилку успішно перехоплено:", err.message);
    return "Відновлено"; // Повернення звичайного значення переводить наступний проміс у стан fulfilled!
  })
  .then((recoveryMsg) => {
    console.log("Конвеєр продовжує нормальну роботу:", recoveryMsg);
  });
```

### 4.4 Поширення помилок та необроблені відхилення (Unhandled Rejections)

Помилка (rejection) «падає» вниз уздовж ланцюжка промісів, ігноруючи всі проміжні обробники успіху `.then(onFulfilled)`, доки не зустріне перший відповідний `.catch()` або `.then(null, onRejected)`:

```
Promise.reject("Критична помилка")
   |
   +--> .then(step1)         [ПРОПУЩЕНО]
   |
   +--> .then(step2)         [ПРОПУЩЕНО]
   |
   +--> .catch(errorHandler) [ОБРОБЛЕНО ТУТ]
   |
   +--> .then(step3)         [КОНВЕЄР ВІДНОВЛЕНО]
```

Якщо помилку не перехоплено жодним обробником у ланцюжку, рушій генерує глобальну подію **`unhandledrejection`**:
* У браузері: `window.addEventListener('unhandledrejection', event => ...)`
* У Node.js: `process.on('unhandledRejection', (reason, promise) => ...)`

# Модуль 5: Сучасні підходи до асинхронного керування потоком

### 5.1 Як `async` / `await` влаштований під капотом

Конструкція `async` / `await` є синтаксичним цукром над **генераторами (Generators)** та **промісами**.

Коли функція з модифікатором `async` зустрічає ключове слово `await вираз`:
1. `вираз` обгортається в `Promise.resolve(вираз)`.
2. Виконання асинхронної функції **призупиняється**, а її локальний контекст зберігається в купі.
3. Реєструється мікротаск, який відновить генератор, щойно проміс перейде в стан settled.
4. Керування негайно повертається в код, який викликав `async`-функцію.

```javascript
// Нативний async/await синтаксис:
async function fetchUserWorkflow(id) {
  console.log("Старт процесу для:", id);
  const user = await fetchUserData(id);
  console.log("Користувача отримано:", user.name);
  return user;
}
```

#### Еквівалент під капотом (Децукрування на базі генераторів та промісів):

```javascript
function fetchUserWorkflowDesugared(id) {
  return new Promise((resolve, reject) => {
    // Генератор зберігає стан між кроками yield
    function* generatorFn() {
      console.log("Старт процесу для:", id);
      const user = yield fetchUserData(id);
      console.log("Користувача отримано:", user.name);
      return user;
    }

    const iterator = generatorFn();

    // Рекурсивна функція-рушій, що обробляє кроки мікротасків
    function step(verb, arg) {
      let result;
      try {
        result = iterator[verb](arg);
      } catch (err) {
        return reject(err);
      }

      const { value, done } = result;

      if (done) {
        return resolve(value);
      } else {
        // Забезпечуємо приведення до Promise та ставимо відновлення в мікротаск
        return Promise.resolve(value).then(
          (nextVal) => step("next", nextVal),
          (err) => step("throw", err)
        );
      }
    }

    step("next");
  });
}
```

### 5.2 Порівняння комбінаторів: `all`, `allSettled`, `race`, `any`

ECMAScript надає 4 статичні методи комбінації промісів:

```
                            КОМБІНАТОРИ ПРОМІСІВ
                                     |
         +---------------------------+---------------------------+
         |                                                       |
   [ Логіка AND ]                                          [ Логіка OR ]
         |                                                       |
  +------+------+                                         +------+------+
  |             |                                         |             |
all()      allSettled()                                 race()        any()
(Усі мають (Чекає на всі;                               (Перший, хто  (Перший, хто
успішно    ніколи не переривається                      завершиться,  успішно
завершитись) аварійно)                                  перемагає)    виконається)
```

| Метод | Умова успішного виконання | Умова відхилення (Rejection) | Основний юзкейс |
| :--- | :--- | :--- | :--- |
| **`Promise.all([...])`** | Усі проміси перейшли у `fulfilled` (повертає масив результатів). | Будь-який проміс перейшов у `rejected` (миттєве аварійне переривання). | Залежні паралельні запити, де потрібні всі дані без винятку. |
| **`Promise.allSettled([...])`** | Усі проміси перейшли у стан settled (байдуже, успіх чи помилка). | **Ніколи не переходить у стан rejected.** Повертає масив об'єктів `{status, value/reason}`. | Незалежні пакетні задачі (наприклад, надсилання аналітики). |
| **`Promise.race([...])`** | Спрацьовує за **першим** промісом, що перейшов у будь-який стан (успіх або помилка). | Відхиляється, якщо найперший проміс відхилився. | Обмеження часу очікування (таймаути мережевих запитів). |
| **`Promise.any([...])`** | Спрацьовує за **першим успішно** виконаним (`fulfilled`) промісом. | Відхиляється тільки якщо **всі** передані проміси впали (повертає `AggregateError`). | Резервні джерела та репліки (потрібна хоча б одна жива відповідь). |

```javascript
const pGood = Promise.resolve("Відповідь Сервера А");
const pBad = Promise.reject("Таймаут Сервера Б");

// Promise.all падає негайно через pBad:
Promise.all([pGood, pBad])
  .then(console.log)
  .catch((err) => console.log("Promise.all відхилено:", err));
// Виведе: Promise.all відхилено: Таймаут Сервера Б

// Promise.any ігнорує помилку Сервера Б і повертає перший успіх:
Promise.any([pGood, pBad])
  .then((val) => console.log("Promise.any успіх:", val));
// Виведе: Promise.any успіх: Відповідь Сервера А

// Promise.allSettled документує всі підсумки:
Promise.allSettled([pGood, pBad]).then((results) => {
  /*
  [
    { status: 'fulfilled', value: 'Відповідь Сервера А' },
    { status: 'rejected', reason: 'Таймаут Сервера Б' }
  ]
  */
  console.log("Promise.allSettled результат:", results);
});
```

### 5.3 Антипатерни та витоки пам'яті

#### Антипатерн 1: Асинхронний виконавець (The `async` Executor Trap)

```javascript
// НЕБЕЗПЕЧНО: передача асинхронної функції в new Promise()
new Promise(async (resolve, reject) => {
  const result = await asyncOperation();
  if (!result) {
    throw new Error("Валідація провалена"); // НЕОБРОБЛЕНА ПОМИЛКА (Uncaught)!
  }
  resolve(result);
});
```
*Чому це небезпечно:* Конструктор `Promise` виконує свою функцію синхронно. Якщо асинхронна функція всередині нього викине помилку після першого `await`, вона залишиться всередині прихованого проміса цієї async-функції й взагалі не викличе зовнішній `reject`.

#### Антипатерн 2: Необмежене накопичення промісів (Витік пам'яті)

```javascript
// ВИТІК ПАМ'ЯТІ: збереження посилань у глобальному масиві
const activeTasks = [];

function registerTask(promise) {
  activeTasks.push(promise);
  // Масив нескінченно росте, оскільки посилання не очищуються після резолву!
}
```
*Виправлення:* Видаляти проміс із колекцій відстеження після завершення його роботи за допомогою методу `.finally()`.

# Модуль 6: Покроковий розбір складних сценаріїв виконання

### 6.1 Комплексний приклад із багатьма чергами

Проаналізуйте наведений нижче фрагмент коду:

```javascript
console.log("1");

setTimeout(() => {
  console.log("2");
  Promise.resolve().then(() => {
    console.log("3");
  });
}, 0);

new Promise((resolve) => {
  console.log("4");
  resolve();
}).then(() => {
  console.log("5");
  setTimeout(() => {
    console.log("6");
  }, 0);
}).then(() => {
  console.log("7");
});

console.log("8");
```

#### Покрокова трасування виконання

| Крок | Call Stack | Черга мікротасків | Черга макротасків | Виведено в консоль |
| :--- | :--- | :--- | :--- | :--- |
| **1** | `console.log("1")` | `[]` | `[]` | `1` |
| **2** | `setTimeout(fn2)` | `[]` | `[fn2]` | |
| **3** | Синхронний виконавець `Promise`: `console.log("4")` | `[]` | `[fn2]` | `4` |
| **4** | Виклик `resolve()` | `[]` | `[fn2]` | |
| **5** | `.then(fn5)` додано до виконаного проміса | `[fn5]` | `[fn2]` | |
| **6** | `console.log("8")` | `[fn5]` | `[fn2]` | `8` |
| **7** | *Синхронний стек порожній! Перевірка мікротасків.* | | | |
| **8** | Виконується `fn5`: `console.log("5")` | `[]` | `[fn2]` | `5` |
| **9** | Всередині `fn5`: виклик `setTimeout(fn6)` | `[]` | `[fn2, fn6]` | |
| **10** | `fn5` повертає undefined; планується `.then(fn7)` | `[fn7]` | `[fn2, fn6]` | |
| **11** | *Мікротаски ще є!* Виконується `fn7`: `console.log("7")` | `[]` | `[fn2, fn6]` | `7` |
| **12** | *Мікротаски порожні! Вибір першого макротаска (`fn2`)* | | | |
| **13** | Виконується `fn2`: `console.log("2")` | `[]` | `[fn6]` | `2` |
| **14** | Всередині `fn2`: `Promise.resolve().then(fn3)` | `[fn3]` | `[fn6]` | |
| **15** | *Стек порожній! Очищення мікротасків перед наступним макротаском!* | | | |
| **16** | Виконується `fn3`: `console.log("3")` | `[]` | `[fn6]` | `3` |

| **18** | Виконується `fn6`: `console.log("6")` | `[]` | `[]` | `6` |

### 6.2 Каскади мікротасків у подіях DOM

Класичний приклад різниці між **фізичним кліком користувача** та викликом програмного методу `.click()`.

```javascript
const button = document.createElement("button");
document.body.appendChild(button);

button.addEventListener("click", () => {
  Promise.resolve().then(() => console.log("Мікротаск 1"));
  console.log("Слухач 1");
});

button.addEventListener("click", () => {
  Promise.resolve().then(() => console.log("Мікротаск 2"));
  console.log("Слухач 2");
});

// Сценарій А: Реальний клік мишею користувача
```

**Результат сценарію А (Реальний клік):**
```text
Слухач 1
Мікротаск 1
Слухач 2
Мікротаск 2
```
*Чому?* Браузер викликає кожен обробник як окремий макротаск. Коли перший слухач завершується, стек викликів повністю звільняється. Відбувається **Microtask Checkpoint**, який одразу виконує «Мікротаск 1», і лише після цього браузер викликає другого слухача.

```javascript
// Сценарій Б: Програмний виклик через JS
button.click();
```

**Результат сценарію Б (Програмний виклик):**
```text
Слухач 1
Слухач 2
Мікротаск 1
Мікротаск 2
```
*Чому?* Метод `.click()` викликається синхронно і знаходиться у Call Stack. Коли завершується перший обробник, стек не порожній — там все ще активний виклик `button.click()`, який одразу синхронно запускає другого слухача. Мікротаски зможуть виконатися лише після того, як завершаться обидва слухачі й метод `.click()` залишить стек.

# Модуль 7: Вправи для самоперевірки та завдання з дебагінгу

### Вправа 1: Пакетний оновлювач на базі мікротасків (Batcher)

Реалізуйте механізм, який акумулює синхронні оновлення стану й викликає обробник лише один раз у найближчому мікротаску.

```javascript
class Batcher {
  constructor(flushCallback) {
    this.queue = new Map();
    this.isScheduled = false;
    this.flushCallback = flushCallback;
  }

  set(key, value) {
    this.queue.set(key, value);
    if (!this.isScheduled) {
      this.isScheduled = true;
      // Плануємо скидання черги в мікротаску
      queueMicrotask(() => {
        const snapshot = new Map(this.queue);
        this.queue.clear();
        this.isScheduled = false;
        this.flushCallback(snapshot);
      });
    }
  }
}

// Перевірка роботи:
const batcher = new Batcher((batchedMap) => {
  console.log("Пакет опрацьовано. Кількість ключів:", batchedMap.size);
  console.log("Фінальне ім'я:", batchedMap.get("name"));
});

batcher.set("name", "Олена");
batcher.set("age", 28);
batcher.set("name", "Іван"); // Перезаписує ім'я
console.log("Усі операції додано синхронно");

// Вивід у консоль:
// Усі операції додано синхронно
// Пакет опрацьовано. Кількість ключів: 2
// Фінальне ім'я: Іван
```

### Вправа 2: Передбачте послідовність виконання

Проаналізуйте код без запуску:

```javascript
async function first() {
  console.log("A");
  await second();
  console.log("B");
}

async function second() {
  console.log("C");
}

console.log("D");
first();
console.log("E");
```

**Правильний вивід:**
```text
D
A
C
E
B
```

**Пояснення:**
1. `console.log("D")` виконується синхронно $\rightarrow$ `D`.
2. Викликається `first()`. Виводиться `console.log("A")` $\rightarrow$ `A`.
3. Викликається `second()`. Виводиться `console.log("C")` $\rightarrow$ `C`.
4. `second()` завершується і повертає вирішений проміс. Оператор `await` формує мікротаск для відновлення `first()` і призупиняє її виконання.
5. Потік повертається в глобальну область. Виконується `console.log("E")` $\rightarrow$ `E`.
6. Стек викликів спорожнів. Event Loop бере мікротаск з черги й повертає керування у `first()`.
7. Виконується `console.log("B")` $\rightarrow$ `B`.

## Чеклист ключових тез для закріплення

* [ ] JavaScript є однопотоковим: єдиний Call Stack із суворим правилом Run-to-Completion.
* [ ] Event Loop надає безумовний пріоритет **Черзі мікротасків** перед **Чергою макротасків**.

* [ ] Нескінченна рекурсія мікротасків призводить до голодування (starvation) макротасків і зависання UI.
* [ ] Реакції промісів (`.then`, `.catch`, `.finally`) завжди реєструються як мікротаски, навіть якщо проміс уже вирішений.
* [ ] `async`/`await` — це синтаксична надбудова над генераторами та мікротасками промісів.
